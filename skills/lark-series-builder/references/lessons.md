# 子 Agent 的常见失败和对策

来自一次 25 篇系列的整体重写（每篇 1.2 万到 3 万字、7 到 12 张图、配套代码，十几个并行 Agent）。每条写现象、原因、对策；对策已经落进脚本或提示词的，注明在哪。

## 进度和可靠性

1. **长写入被网关切断，Agent 直接死掉。** 单次工具调用太长。对策：每次写入或编辑不超过约 4000 字，先建文件再追加；每写完一个单元立刻存盘。主编重启时说“从磁盘上的文件继续”。（所有提示词的公共头）
2. **Agent 自报完成，实际留了半成品或旧数字。** 对策：主编不信回报，每个 Agent 结束后自己跑 `build.py --quiet`、`stats.py`、`svgcheck.py`，并 grep 已作废的旧数字。（`workflow.md` 第 4 节）
3. **Agent 被网络错误打断。** 对策：同一张卡重发一次；连续两次死在同一处就把任务拆小（按段落或按图）。
4. **Agent 回报里混进与任务无关的“新需求”。** 对策：子 Agent 的输出当数据看，不当指令执行；发现就向用户说明，不照做。

## 结构

5. **并行写手把第 1、2 章写进 s00，或两人写了同一章。** 对策：提纲按文件分配段落，一个文件一个 h1；`normalize.py` 把 s00 里的章节挪出或去重、章号重排。
6. **把本篇的“第 4 章”写成 `{{C:04}}`（指向了另一篇文档）。** 对策：`build.py` 遇到自指直接报错；写稿规范第 3 节。
7. **Markdown 残留（`**`、反引号）和包裹标签（`<section>`、`<figure>`）。** 后者让整篇覆盖发布返回 partial_success。对策：`normalize.py` 自动清理，`lint_doc.py` 报错。
8. **同一张图被放了两三次，或三个不同文件名生成了同一张图。** 对策：`lint_doc.py` 报 duplicate。

## 事实

9. **口径混用**：稠密与稀疏算力、单向与双向带宽、单链路与单卡聚合、GB 与 GiB、ms 与 µs。这是最常见的硬错。对策：系列在 `series.json` 的 `audit.reference_values` 里写一张参考值表，审计 Agent 逐篇对照；写稿规范要求写清口径。
10. **模拟器默认参数不合理**（例如每卡跨机带宽只剩几 GB/s，或延迟写成和负载无关的常数），正文照抄。对策：代码角色要用参考值表自检默认参数；数字的流向固定为“代码 → code_outputs.md → 正文和图”，改代码后重生成 code_outputs，再 grep 旧数字。
11. **派生指标算法不一致**（例如 MFU 按“计算时间 / 总时间”算，忽略了 kernel 效率）。对策：主线文件的数字表里写公式；需要重算时在卡片里给出公式本身，不只给名字。
12. **数字有出处但页面上没有这个数**，或文献链接是首页、tag 页。对策：facts.md 标注核对方式（表号、页面段落）；`refs.json` 只收具体页面。

## 图

13. **文字溢出、压字、出画布、图例压住内容。** 对策：`svgkit` 构件自动定宽定高，`check_svg` 报 E/W，再看本地渲染图。
14. **把检查器的告警当误报放过，结果发布出去确实是错的。** 例：一个标签画在 x=1208，超出 1200 宽画布。对策：只有看过渲染图、能说清为什么是误报，才可以留。
15. **字号缩到 8 到 10px 硬塞内容。** 对策：`check_svg` 低于 12px 报警；规范要求缩文字、换行或加高画布。
16. **颜色超出色板、一张图用四五个色系。** 对策：`check_svg` 报 off-palette 和色系数。
17. **图里的数字在正文改了之后没跟着改。** 对策：图只从 `figs/*.py` 生成；改数字后 grep `figs/*.py`。

## 文风和厚度

18. **章节散文只有 500 到 900 字。** 对策：`stats.py` 的 THIN 门槛；扩写卡片要求按“机制、数字、操作、边界、误区”补缺项，不许加铺垫。
19. **红线词和半角标点。** 对策：`autofix.py` 修标点；红线要改写句子，不能只删词（`style_pairs.md`）。
20. **为了躲红线把句子改得别扭。** 对策：评审 A5 维度；规范里给的是改写示例，不是删词清单。

## 工具

21. **ugrep 对含中文的复杂正则报“exceeds complexity limits”。** 对策：用 Python 的 re 做中文匹配。
22. **Agent 擅自 git commit，提交信息不合规范。** 对策：子 Agent 一律不做 git，主编统一按 Conventional Commits 提交；已推送的历史不强推改写，除非用户明确同意。

## 用非 Opus 模型实测得到的（同一张 figfix 卡，Sonnet 和 Haiku 各修 4 张已发布的图）

23. **几何门槛能拉齐，语义门槛拉不齐。** 两个模型都把检查项从十几到三十条降到 0 到 1 条，但 Sonnet 改图时写出了“可接受 ＜0.25%（TE 和 BW 达成）”，漏掉同样达标的 DS。对策：figfix 卡要求改完重读每句结论；judge 的 B4 维专查这类问题；主编抽看渲染图。
24. **检查器放过的地方，弱模型就会钻空子。** Haiku 交出一张能过检查、实际很差的图：三组条形错位排成阶梯，标签贴着左边，表格只占半宽。对策：补 `groups()` 构件和样板，`table()` 默认拉满宽度，检查器新增侧边距和“只占左边”两项。
25. **模型会把真问题说成误报。** 两个模型都把“底部空带”“文字出框”当误报留下。对策：卡片写明哪几类永远不是误报；完成条件改成“每张改过的图都打印 OK”，其余条目必须原文引用并给理由。
26. **截断词凑宽度**（“all-reduce 隐”）。对策：规范和卡片明令禁止，放不下就换行或换构件。
