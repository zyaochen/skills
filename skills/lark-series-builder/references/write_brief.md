# 写稿规范

适用于系列里每一篇正文（总览篇另见文末）。数值阈值都在 config `thresholds`，下文写的是默认值；系列在 `spec/series.json` 覆盖时以覆盖值为准，`spec/QUICK.md` 里是渲染后的实际值。

## 1. 一篇文档的骨架（顺序固定）

1. `<title>`：registry 里的标题，一字不改。标题直接摆判断或“主题：要点”，不带年份、版本号、破折号。
2. 🎯 开篇 callout，两到三段：
   - `<p><b>这篇文档解决什么问题</b>：……</p>`：先写线上会看到的现象和背景，再列读者会遇到的一串具体问题。
   - `<p>使用方式：……</p>`：哪类读者先读哪几章；末句固定“文中版本、规格和基准数字核对于 {verified_on}。”
   - 有配套代码时加 `<p><b>代码</b>：<a href="仓库目录链接">目录名</a>。……</p>`：每个文件做什么、哪些 CPU 能跑、哪些要 GPU 或特定环境。只写真实存在的文件。
3. 系列有主线时（config `template.position`），callout 后紧跟一段主线位置：上一篇处理了什么，本篇处理主线上的哪一项，读完瓶颈或问题会转到哪，由下一篇接手。上一篇、下一篇用 `{{C:NN}}`。
4. `<h1>导读 · 先给结论</h1>`：5 到 7 条 `<li><b>一句结论。</b>依据和数字{{r:key}}</li>`，每条都能单独转述。接一张总览图。再接一段 `<p><b>📎 与系列其他文档的分工</b>：……</p>`，把相邻主题分到具体篇，本篇只深挖 registry `focus/scope` 那一项。
5. 8 到 13 个 `<h1>第 N 章 · 标题</h1>`，每章 2 到 4 个 `<h2>N.M 标题</h2>`：
   - 第 1 章交代问题本身：用一个具体现象开场，说明它在主线（或全篇问题）里的位置，配一张图。
   - 中间各章按“原理与账本 → 工具与源码 → 动手 → 常见误区”推进。系列定义了方法闭环时（config `template.required_terms`），至少一章是完整案例，正文显式出现每个步骤词，前后数字来自配套代码的真实输出或带引用的公开数据。
   - 每章末一个 🔑 `<p><b>本章要点</b>：……</p>`，末句点明本章解决了主线上的哪一项。
   - 全篇 3 到 6 个 💡 `<p><b>常见误区</b>：……</p>`，每个写现象、原因、改法。
   - 最后一章是落地章（标题含 config `last_chapter_contains`，默认“清单”）：📌 `<p><b>上线前核对清单</b></p><ul>…</ul>`，4 到 6 道自测题带答案要点，一段“接下来的问题在哪”衔接下一篇。
6. 参考文献由 build 生成，不写进分段。

## 2. 厚度：一章要写到什么程度

“厚”指信息密度高，不靠堆字数。机器门槛由 `stats.py` 检查：每章散文汉字不少于 `chapter_cjk_min`（默认 1400），目标 1800 到 3000；每章至少 3 个不同引用；除清单章外每章至少一张图；不能一章里只有散文、没有表格、代码块或图。

一章合格的标志，每条都要能在正文里指出来：

| 要素 | 说明 | 反例 |
|---|---|---|
| 论点 | 章首一两句给本章判断 | 章首写“本章介绍 X” |
| 机制 | 讲清为什么会这样，到读者能自己推一遍的程度 | 只列现象和结论 |
| 数字 | 至少 3 个具体数字，带口径和出处 | “显著提升”“大幅下降” |
| 操作 | 命令、配置项、API、指标名，读者能照着做 | “可以用相关工具分析” |
| 边界 | 什么条件下不成立、代价是什么 | 只讲好处 |
| 误区 | 一线最常见的错法和改法（可放 💡） | 无 |
| 图或表 | 把本章最难用文字讲的那件事画出来 | 图只复述段落 |

扩写时按这张表补缺的那一项，不加铺垫句、不重复上一章、不加“总之”“综上”式的收尾段。

## 3. 分段与占位符

- 正文写成 `drafts/NN/seg/s00.xml … sKK.xml`，s00 只放 title、开篇、主线位置、导读、分工；之后每个文件一个 `<h1>第 N 章 · …</h1>`，文件名顺序就是阅读顺序。
- 引用 `{{r:key}}`（多个写 `{{r:a,b}}`），key 必须在 `refs.json`。不写裸 `[n]`，不手写 `<a href>[n]</a>`。
- 系列内链接 `{{C:NN}}` 只指别的篇；指本篇自己的章节一律写“第 N 章”，绝不写成 `{{C:本篇号}}`。不写别篇的章节号（别篇在并行改，章节号会变），写“见 {{C:13}} 讲 ring 带宽的部分”这种主题指向。
- 图 `{{F:name}}` 单独成段，不包 `<p>` 或 `<whiteboard>`；对应 `figs/name.py` 生成的 `figs/name.svg`。同一张图只放一次。

## 4. 标记（飞书 XML 子集）

- 只用：`<title> <h1>-<h3> <p> <b> <code> <a href> <ul>/<ol><li> <table> <callout> <pre lang caption><code> <cite>`，图由 build 生成 `<whiteboard type="svg">`。li 里直接写字。
- callout：`<callout emoji="💡" background-color="rgb(255,245,235)" border-color="rgb(255,186,107)">`，所有 callout 同色（config `template.callout_color`），里面只放 `<p>` 和 `<ul>`，粗体标签开头。
- 表格：`<table><colgroup><col width="160"/>…</colgroup><thead><tr><th background-color="rgb(240,244,255)" vertical-align="top"><p>表头</p></th>…</tr></thead><tbody><tr><td vertical-align="top"><p>内容</p></td>…</tr></tbody></table>`，列宽总和 700 到 820。
- 代码块：`<pre lang="bash" caption="一句说明"><code>…</code></pre>`。
- `&` 写 `&amp;`，正文里的 `<` 写 `&lt;`。不用 Markdown（`**`、反引号、`#`）、`&nbsp;`、图片、`<section>` `<figure>` `<div>` 这类包裹标签（会让整篇覆盖发布部分失败）。

## 5. 文风

机器扫的（`lint_doc.py`，只扫散文，表格、代码、图、cite 先剥掉）：

- 红线清零：“不是 X 而是 Y”“不在 X 而在 Y”、破折号“——”、“进行”、“完成了”、“一是……二是”、“第一，……第二，”、量词标题（“三板斧”“五个维度”）。
- 标点清零：中文旁边的半角 `, ; : ? ! (`，夹着中文的半角直引号。中文引号用“”。
- 密度项（每万字上限）：“而不是”“实现”、三段以上箭头链、口号词。不要求清零，超了就改。
- 平均句长 15 到 32 字。

机器扫不出、评审会扣分的（`rubric.md`）：

- 读者是有经验的工程师。每段先结论后依据，写完整句子，不用口号。术语第一次出现给中文说明，英文放括号。
- 每个具体数字、版本、日期都有出处：公开资料带引用，自己算的写明“本篇 sim_xxx.py 输出”。厂商数字写清口径（稠密或稀疏、单向或双向、单卡或整机、峰值或实测）。不编数字。
- 不用量词标题，不造新词，比喻只用来解释读者不懂的概念。
- 不写人名（论文署名除外）、邮箱、open_id，不引用内部文档和内部数据。

改写示例见 `style_pairs.md`，写之前读一遍。

## 6. 总览篇（hub）

总览篇不按章节模板写，但要做到：一句话主线和它的记账式（或问题框架）；一张全系列地图（分层、每篇一格、标出主线项）；按层的表格，每篇一行（篇名用 `{{C:NN}}`、回答什么问题、主线项、配套代码目录）；两到三条学习路线（按读者角色）；版本基线；怎么用配套代码。每一篇都要从总览链到（`series_check.py` 检查）。
