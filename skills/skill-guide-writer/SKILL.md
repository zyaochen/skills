# skill-guide-writer

> 面向“已有能力”的文档生成器：把分散的契约、脚本、示例、测试和网页资料整理成用户能直接上手的指南。默认本地证据优先，外部资料只做补充，不覆盖本地已验证行为。

## Success Criteria

- 用户拿到文档后，能在不追问的情况下完成第一次成功使用，或明确知道当前为什么不适用
- 每个关键结论都能追溯到本地文件、命令输出或已核验网页
- **事实** 与 **推断/建议** 分离，不混写成“像事实一样”的建议
- 增量更新模式下，变化点一眼可见，且全文仍能独立阅读

## When to use

- 用户要某个 skill / tool / plugin 的 Quick Start
- 用户要完整使用手册、FAQ、升级说明、Developer Reference
- 用户已有旧版指南，需要按新行为增量更新
- 你已经有本地源码、现有文档或公开网页，可以据此整理指南

## When NOT to use

- 还没有现成能力，只是想“设计一个新 skill” → `skill-creator`
- 目标是评估某个 skill 为什么不触发 / 怎么提分 → `skill-refiner`
- 目标是外部知识吸收并沉淀为新 capability → 不在本 skill 范围
- 用户只是要一个简短口头解释，不需要成体系文档 → 直接回答

## 默认假设

- 未指定目标读者 → 默认“第一次上手的日常用户”
- 未指定输出介质 → 默认直接在聊天内交付
- 未指定层级 → 默认输出 **L2 + L3**
- 用户说“更新指南”但未提供旧文档 → 仍基于当前本地证据输出一份完整更新版，并明确是按最新证据重写
- 用户要求“只基于本地事实” → 不补写网页信息，也不扩写推断型最佳实践

## 输入优先级

按以下顺序取证，缺什么补什么：
1. 本地 `SKILL.md` / `references/` / `scripts/` / 测试
2. 仓库内 README、示例命令、变更日志、最近 diff
3. 用户提供的 URL 或公开网页（`WebFetch` / `WebSearch`）
4. 用户补充的现有指南、更新说明或目标受众信息

如果核心事实仍不够，最多做一次打包澄清。

## 证据裁决规则

1. **可执行证据优先**：脚本 / 测试 / 真实命令 > `SKILL.md` / `references/` > README / 注释 > 外部网页
2. **本地证据优先**：网页只补充本地没有的事实，不覆盖本地已验证行为
3. **冲突时优先执行面更近、更新更近的来源**；若正文采用了其中一方，明确说明依据
4. **裁决不了就显式留白**：写 `> ⚠️ 待确认：...`，不要猜测补齐

## 一次性澄清包

只有在核心信息缺失且无法从本地发现时，才打包问一次。优先合并为一组：
- 要写的是哪个能力（名称 / 路径 / URL）
- 目标读者是谁（首次使用者 / 日常用户 / 维护者）
- 聊天内输出还是落 Markdown 文件
- 是新写指南，还是更新已有指南

若本地证据已经足够，不要为了“更完美”继续追问。

## 标准工作流

### Step 1 — 定义交付目标
- 确认对象、读者、输出介质、是否增量更新
- 用户没指定时，采用默认假设直接推进

### Step 2 — 收集证据
- 至少覆盖 3 类证据：主契约、一个执行入口、一个示例或测试
- 如果是升级说明，额外读取变更日志、旧指南或最近 diff
- 区分 **证据**（文件 / 命令 / 输出）与 **推断**（推荐用法 / 风险提醒 / 迁移建议）
- 只要本地证据足够，优先在文中引用具体文件路径或命令，而不是抽象占位词

### Step 3 — 选输出层级
- 默认输出 **L2 + L3**
- 若用户要求“简短 / 概要 / one-pager” → L1
- 若用户要求“完整 / 详细 / 二次开发 / developer reference” → L2 + L3 + L4
- 分层定义见 [references/output-levels.md](references/output-levels.md)

### Step 4 — 生成指南
最少包含：
- 适用对象与前置条件
- 最短成功路径
- 1 个端到端示例
- 常见错误与修复
- 边界：能做什么、不能做什么、该配合谁

推荐输出骨架：
1. 最短成功路径
2. 适用对象与前置条件
3. 端到端示例
4. 日常用法 / 功能分模块说明
5. 常见错误与修复
6. 边界与相邻能力
7. 事实 vs 推断 / 建议
8. Developer Notes（仅 L4 或用户明确要求时）

Quick Start 默认额外要求：
- 第一段先给出**最短成功路径**，不要把背景说明放在最前面
- 如果本地证据里已有命令、参数名或文件路径，直接复用，不改写成抽象占位词
- 若某条建议属于推断而非事实，要显式标成“推断”或“建议”
- 若要求落文件，优先复用仓库里已有的 `docs/`、`guides/` 或现有文档路径；没有现成结构时再新建最小必要文件

### Step 5 — 增量更新模式
当用户说“更新指南 / skill 升级了 / 加了新功能”时：
1. 读取现有指南或旧版本说明
2. 对照本地新行为与新增参数
3. 先给一段简短变更摘要，再输出**完整更新后的文档**
4. 必要时用 `[NEW]` / `[CHANGED]` / `[DEPRECATED]` 标注变化
5. 不输出“待补充”占位符；确实缺信息时，用 `> ⚠️ 待确认` 明示

标记示例：
- `[NEW]` 新增 `--format table` 示例
- `[CHANGED]` Quick Start 现在默认先给最短成功路径
- `[DEPRECATED]` 旧参数 `--legacy-mode` 已不建议继续使用

### Step 6 — 质量自检
按 [references/quality-rubric.md](references/quality-rubric.md) 检查：
- 覆盖度
- 可操作性
- 一致性
- 证据可追溯性
- 增量更新标记是否准确

## 事实与推断分离

默认把内容分成两类：
- **事实**：来自本地文件、脚本、测试、README、命令输出、已核验网页
- **推断 / 建议**：基于事实归纳出的推荐用法、风险提醒、迁移建议

如果用户要求“只基于本地事实”，就不要补写推断型最佳实践。

## 反模式

- 开头先铺很长背景，导致最短成功路径被埋住
- 把仓库里真实存在的命令 / 参数 / 路径改写成抽象占位词
- 把“建议这样做”写成“它就是这样工作”
- 只罗列功能，不解释边界、依赖和相邻能力
- 明明证据不足，却假装已经验证
- 用“待补充”“后续完善”当交付物收尾

## 输出约束

- 默认 GitHub-flavored Markdown
- 示例优先使用可复制命令或最小输入 / 输出片段
- 不捏造命令、参数、权限、成功结果
- 若内部文档当前不可访问，明确写“依据不足”，不要假装已验证
- 如用户只要聊天内结果，可直接输出；如用户要文件化文档，可落 Markdown 文件
- 若关键结论来自本地文件，优先引用具体文件路径；若来自网页，明确它是外部补充信息
