# 验证：证据够不够

裁判只能证明"约定的命令在约定的提交上得到了约定的结果"。这句话之外的所有判断，都要由智能体说清楚依据，并且让人看得出哪些是测出来的、哪些是推断的。

## 1. 风险对应证据

| 风险 | 需要的证据 |
|---|---|
| 测试根本没有复现缺陷 | `verify` 的红绿检查：测试在基线源码上失败（`baseline_red: true`）、在最优提交上通过 |
| 修复只对复现输入有效 | 复现测试之外，覆盖边界值与相邻输入的测试 |
| 修复破坏了别的行为 | 回归测试全部通过；受影响但未覆盖的行为在评审说明里列出 |
| 蓝图元素"有名无实" | 节点的 `accept` 命令覆盖该元素的关键路径；回归检查为绿；竣工图与代码对应 |
| 优化只是噪声 | δ 高于对照重跑的噪声；`verify` 重跑分数与记录之差小于 δ |
| 优化牺牲了正确性 | 基准之外的正确性测试纳入 `guard_cmd`、`fast_cmd` 或约定命令 |
| 优化牺牲了另一个指标 | 用 `--secondary-regex` 约定次要指标，交付包展示它的变化 |
| 改动绕过了判定依据 | 冻结哈希不变；自检通过；宪法未漂移 |
| 结论没有出处或出处被改写 | 每条论断的摘录逐字对得上来源快照；快照 `intact`；每个问题的独立来源域名数达到 `min_sources`（镜像只算一个）；开启 `cite_numbers` 时每个数字都在所引摘录里 |
| 文档"看起来像样"但没回答问题 | 逐问题 `accept` 命令；`min_chars` 与必需章节；骨架草稿过不了硬检查（`init` 的区分度检查） |
| 评审打分不可信 | 好 / 差样本校准通过；评审与写作用不同模型；分差大于噪声；草稿里的注入文本被硬检查拦下 |
| 设计在没人想到的交错下出错 | 形式化约定案例 verified（退出码 0、完成消息级别 0、状态数大于 0），检查器 jar 哈希与契约一致；需求与性质双向覆盖；故障动作进入动作组合；`unmodeled` 与有界参数在交付包里列明 |
| 任务"说做完了" | `plan done` 只认运行目录的达标 + 有效验证（+ 批准），或 `check` 命令退出码 0 |
| 结果依赖本机状态 | `side_effects` 已处理；生成路径已声明；验证在干净工作区上进行 |

## 2. 有意义的基线

基线必须真正区分"做到"和"没做到"：

- 修复：复现测试在修复前失败，并且失败原因就是这个缺陷。`init` 检查它在基线上失败，`verify` 再在临时检出的基线源码上复查一次，防止"第一次跑恰好失败"的假红。
- 开发：回归检查在基线上的结果被记录下来，交付时能看出变化来自本次工作。
- 优化：基线干净跑通，噪声已测量且低于 δ。

基线本身不可信时，后面所有的对比都不可信。

## 3. 三类陈述

写评审说明和交付结论时，每一句话都应该能归入下面一类，并且标注清楚：

- **已观察**：裁判记录的事实——命令、退出码、分数、哈希、提交号，附 `raw/` 下的日志路径。
- **AI 评估**：智能体基于读代码作出的判断——"这个改动不影响并发路径"。要写出依据。
- **未验证**：没有被任何命令覆盖的行为、没来得及跑的场景、环境差异。必须明说。

不要把"AI 评估"写成"已观察"的语气。

## 4. 交付前最后检查

- [ ] `status` 显示 `decision: handoff`、`head_is_best: true`、`worktree_clean: true`。
- [ ] 冻结文件未改动，宪法未漂移。
- [ ] `verify` 在当前最优提交上通过，且之后没有新的接受。
- [ ] `review.md` 写完，三类陈述分开。
- [ ] `report` 在 `verify` 之后运行，交付包未被手工修改。
