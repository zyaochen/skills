## 1. 通用规则

- **每个改动都要经过裁判**：提交一个 commit，然后运行 `attempt`。被拒绝（`rejected`）或无效（`invalid`）的尝试会被自动回滚到最优提交；被接受的成为新的最优。
- **尝试必须建在最优之上**：HEAD 必须是当前最优提交的后代，否则 `attempt` 直接拒绝（退出码 3，不做任何改动）。
- **一次尝试只检验一个想法**，`--note` 写清楚改了什么、为什么。
- **不要碰判定依据**：冻结文件、蓝图、宪法、契约、记录文件都不能改；想改约定，回到澄清并 `init --renew`。
- **不要在工作区的 `.evloop/` 下写任何东西**：那里的文件被忽略，git 看不到，回滚也清不掉，`start`、`status` 都会把它当成问题报出来。运行目录在工作克隆里，不在循环工作区里。
- **底线检查与快速预检**：契约带有宪法的 `guard_cmd` 时，它在每次尝试的约定命令之前运行；带有 `fast_cmd`（`init --fast-cmd` 或宪法）时，它紧接着运行。任何一个失败即判无效（记录里的 `stage` 写明是 `guard` 还是 `fast`），完整测试根本不跑，省下的时间留给下一次尝试。
- **读失败要看摘要**：未通过的尝试，记录里有 `failure`（命中 error / fail / assert 等关键词的几行，没有命中时取最后几行），`attempt` 的输出里还附带原始日志的最后 `--tail` 行（默认 20，`--tail 0` 关闭；只打印、不写入记录）。先读它们再决定下一步，需要全貌时再打开 `raw/` 下的日志。
- **每条记录都带改动规模**：`diff` 字段是相对最优提交的增删行数，交付包会显示。

## 2. 过程可见

每次 `attempt` 之后，用一两句话告诉人：试了什么、裁决是什么、下一步打算做什么。阶段性节点（一批元素完成、一条路线被证伪、预算过半）运行 `report --progress` 并给出页面路径。不要让人对着一段沉默猜进度。

## 3. 创建工作区并开始

```bash
git worktree add -b evloop/<task> ../<repo>-evloop-<task> HEAD
python3 <skill>/scripts/evloop.py --home "$PWD/.evloop/runs/<task>" start \
  --worktree ../<repo>-evloop-<task>
```

`start` 会：

1. 确认工作区是独立的 git worktree（不能是工作克隆本身）、干净、冻结文件与澄清时一致、运行目录不在其中。
2. 把当前 HEAD 记为最优提交（基线），开始计时并写下截止时间（如有预算）。
3. 运行**自检**（smoke）：故意改一个冻结文件、故意提交一个越界文件，确认裁判都能识别，并确认回滚后工作区完好。自检失败说明约定本身有漏洞，回到澄清。可以随时用 `smoke` 重跑；`--no-smoke` 只用于调试。

工作区在分离 HEAD 上，或就在交付目标分支上时，`start` 会告警：交付需要一条独立的 `evloop/<task>` 分支来合并。

## 4. 接手进行中的循环

接手、或上下文被压缩之后，先运行 `resume`：它只读、不加锁，输出一行紧凑 JSON——约定要点（场景、可编辑、冻结、命令、目标）、最优提交与分数、剩余预算、最近几次尝试（`--last N`，默认 5）的裁决与失败摘要、`decision` 与 `next`，以及需要先处理的 `warnings`。它是给智能体"重新上岗"用的最小上下文。

需要完整字段时运行 `status`（加 `--brief` 输出单行 JSON，写在命令的任何位置都可以），读懂这些字段再动手：

| 字段 | 含义 |
|---|---|
| `best` / `best_score` | 当前保留的最优提交与分数 |
| `head` / `head_is_best` | 工作区 HEAD，及它是否就是最优 |
| `worktree_clean` | 是否有未提交改动（生成路径下的除外） |
| `hidden_ignored` | 工作区 `.evloop/` 下被忽略的文件 |
| `frozen_changed` / `constitution_drift` | 冻结文件、宪法是否被动过 |
| `remaining_seconds` | 剩余预算（秒） |
| `attempts_remaining` / `tokens_remaining` | 尝试次数、token 的剩余额度（约定了才有） |
| `decision` / `stop_reason` | `continue` 继续循环；`handoff` 进入交付，`stop_reason` 说明是达成目标还是哪种预算耗尽 |
| `next` | 裁判建议的下一步 |

**先结清在途工作**：工作区有未提交改动，就提交后 `attempt`，或丢弃；HEAD 是未裁决的提交，就对它 `attempt`，或重置回最优。不要在不明来历的状态上叠加新改动。需要全面体检时运行 `doctor`。

## 5. 各场景的循环

**修复**：在批准的影响范围内修改，提交，`attempt`。测试仍失败时裁决为 `failing`（退出码 1），提交被**保留**为新的最优——修复往往要分几步走；测试通过即 `accepted`，`status` 给出 `handoff`。

**开发**：按 `batches` 的顺序实现元素，提交后用 `--elements` 认领：

```bash
python3 <skill>/scripts/evloop.py --home ... attempt --note "加入订单仓储" --elements store
```

- 依赖尚未实现的元素不能单独认领；可以把依赖一并认领。
- 蓝图节点可以带 `accept` 命令（见 [clarify-development.md](clarify-development.md)）：本次认领的、以及此前待定的元素，都要各自的 `accept` 命令通过；任何一个失败，裁决为 `failing`、记录 `accept_failed`，这些元素保持待定，下一次尝试会自动重跑它们的验收命令。
- 有 `--check-cmd` 时：检查为绿（`green`）才算实现；为红（`failing`）时元素进入待定，提交被保留，下一次把检查修绿（不必重复认领）就会算作实现。
- 没有 `--check-cmd` 时：每轮裁决为 `checkpoint`，认领直接生效，等人工检查。
- 全部元素实现后，根据**实际交付的代码**绘制竣工图，写到 `--asbuilt` 路径并提交、`attempt`。竣工图缺元素、无法解析或与蓝图不一致时，`status` 会指出差在哪里。

**优化**：每次尝试必须给 `--route`，为检验的思路起一个短标签（字母、数字、`.`、`_`、`-`）。分数严格好出超过 δ 才接受；否则拒绝并回滚。

- 第一条路线就达标时，`status` 会给出 `handoff`；只要预算还有余量（剩余 5 分钟以上、尝试次数未用完），先按 `next` 的提示再试一条**不同的**路线，再 `verify`。被拒绝也没关系，它是"这条路不比现有方案好"的证据。
- 没有约定 `--target`（纯改进模式）时，`status` 只会在预算耗尽时给出 `handoff`；每条路线都试过、继续试也只是重复时，如实停下来向人报告。

- 约定了次要指标（`--secondary-regex`）时，每次尝试都必须能提取到它，否则判无效。
- 约定了 `--prefer-simpler` 时，还有一条**简化规则**：分数与最优持平（没有变差到 δ）、次要指标没有变差、并且这次改动**净删除**代码，也会被接受，记录带 `simplified: true`。简化被保留为新的最优提交，但 `best_score` 不变——过程图上的最优阶梯线不会因此移动。用它来清理为了冲分而堆起来的复杂度。

## 6. 路线账本

被拒绝、或带原始日志的无效尝试，会把它的路线记为"在当前最优之上已证伪"。`status` 的 `ruled_out` 列出这些路线。

- 想在同一最优之上再试一条已证伪的路线，必须用 `--differs "这次的不同之处"` 说明，否则 `attempt` 拒绝。
- 最优提交变化后，账本重新计算——在新的基础上，旧路线可能重新有效。
- 路线标签要稳定、有意义（如 `index-cache`、`batch-io`），交付时会按路线统计接受 / 拒绝 / 无效次数。

## 7. 为过程图留好记录

优化场景的过程图直接来自 `attempts.jsonl`：每一次尝试的分数、裁决、路线都会画出来。所以不要在裁判之外"偷偷试"——没经过 `attempt` 的尝试不会出现在图上，也不会被承认。

## 8. 预算与预留

三种预算可以任意组合，任何场景都能用：

| 预算 | 约定方式 | 耗尽时的 `stop_reason` |
|---|---|---|
| 墙钟时间 | `--budget-minutes`（优化场景必填）与 `--reserve-minutes` | `time budget exhausted` / `reserve window reached` |
| 尝试次数 | `--max-attempts N` | `attempt budget exhausted` |
| token | `--token-budget N`，每次 `attempt --tokens K` 上报产出这次尝试的用量 | `token budget exhausted` |

任何一种耗尽后，新的 `attempt` 会被拒绝（退出码 3；未裁决的 HEAD 会被回滚并记为无效），`status` 给出 `handoff`。约定命令本身也受剩余时间限制，超时会被整组杀掉并判无效。token 用量由智能体如实上报，裁判只负责累计与截断；不上报就等于没有这项预算。

## 9. 并行生成、串行裁决

可以同时在几个分支上准备候选（例如几个子智能体各试一条路线），但裁决必须一个一个来：

```bash
git -C "$WT" branch cand-a <最优提交>      # 子智能体在 cand-a、cand-b 上各自提交
python3 <skill>/scripts/evloop.py --home "$RUN" attempt --commit cand-a --route a --note "..."
python3 <skill>/scripts/evloop.py --home "$RUN" attempt --commit cand-b --route b --note "..."
```

`--commit` 要求工作区 HEAD 就是最优、工作区干净，候选必须建在**当前**最优之上；裁判把工作区切到候选再裁决，接受则循环分支前进到候选，否则回滚。第一个候选被接受后，最优变了，其余候选需要先变基到新的最优之上，否则会被拒绝（退出码 3）。

## 10. 交付前的验证规则

`verify` 在最优提交上重跑约定命令：

- 修复：测试必须再次通过；并且裁判会在临时 worktree 里检出**基线源码**、套上当前的冻结测试再跑一次，它必须仍然失败（`baseline_red: true`）——否则测试不能证明修复有效，验证失败。
- 开发：回归检查必须再次通过，蓝图里每条 `accept` 命令都要通过。
- 所有场景：冻结文件不被改动。
- 优化：重跑分数与记录的最优分数之差的绝对值必须**小于 δ**，并且达标结论与记录的一致。
- 研究 / 文档：全部硬检查、来源快照完整性、逐问题验收命令再跑一次；配置了细则评审时重新采样，中位数仍须达到通过线。

验证失败说明结果不可复现，不要交付"通过"的结论。

## 11. 研究与文档场景的循环

- 先 `source add` 登记来源，再写论断；论断的 `quote` 从快照里原样摘录，不要凭记忆改写数字或措辞。
- 还没有接受过任何版本时，未写完的草稿判 `failing` 并保留，可以一节一节往上加；一旦有版本被接受，之后的回退判 `rejected` 并回滚。
- 编造引用、摘录对不上、草稿里出现给评审下指令的文字，一律判无效。规则详见 [clarify-research.md](clarify-research.md)。

## 12. 跨会话推进

循环属于计划里的某个任务时，一个会话只推进这一个任务：`status` 为 `handoff` 并 `verify`、`report` 之后，回到计划运行 `plan done`，再用 `plan prompt` 排期下一会话。见 [plan.md](plan.md)。

## 13. 卡住时如实报告

如果连续多次尝试都无法推进（同一个失败反复出现、所有路线都被证伪、约定本身有问题），停下来向人报告：试过什么、证据在哪里（`raw/` 下的日志）、你判断卡在哪里、需要人决定什么。不要为了"做完"去放宽约定。
