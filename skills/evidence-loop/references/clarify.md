# 澄清：把约定一次谈清楚

澄清阶段的产出是一份**封存的契约**。之后循环里的每一次裁决、交付时的每一条结论，都只依据这份契约。约定含糊，后面所有的"通过"都没有意义，所以这一阶段宁可慢。

## 1. 选场景

| 用户的目标 | 场景 | 判定依据 |
|---|---|---|
| 某个行为错了，要改对 | `bugfix` | 一条修复前失败、修复后通过的测试命令 |
| 要新增或重构出一个结构 | `development` | 蓝图（元素 + 依赖）与可选的回归检查命令 |
| 某个指标要变好 | `optimization` | 输出单一数字的基准命令 + 目标线（人不设线时可省）+ 时间预算 |
| 调研并给出处 | `research` | 冻结的文档规格 + 论断文件（每条论断逐字对得上来源快照）+ 可选细则评审 |
| 写使用说明、设计文档 | `document` | 冻结的文档规格（必需章节、篇幅、逐问题验收命令、doctest） |

任务太小（改个错别字、一行配置）时不要启用这套流程，直接改更快；完成标准写不成一条命令时，先和人把标准谈清楚。一个请求同时包含多种目标时，拆成多个任务，各自一份契约、各自一个运行目录。确定场景后读对应的细则：[clarify-bugfix.md](clarify-bugfix.md)、[clarify-development.md](clarify-development.md)、[clarify-optimization.md](clarify-optimization.md)、[clarify-research.md](clarify-research.md)。改动触及共享状态、重试 / 超时、崩溃恢复或所有权时，在前三个场景上叠加形式化设计验证，见 [clarify-formal.md](clarify-formal.md)；几天、几十个会话的大需求先用计划拆分，见 [plan.md](plan.md)。

## 2. 划定生产边界

和人确认三类路径：

- **可编辑**（`--editable`）：循环只能改这些路径。尽量窄；`.` 表示整个仓库，只在确有必要时使用。
- **冻结**（`--frozen`）：判定依据本身——测试、基准脚本、蓝图、夹具。循环中被改动的尝试一律判无效。修复与优化场景必须至少冻结一项（命令行或[项目宪法](constitution.md)都可以提供）。
- **生成**（`--generated`）：约定命令运行时会写出的产物目录（构建输出、缓存）。其中未跟踪的文件不阻塞尝试，回滚时被清掉；但如果把它们提交进尝试，判为无效——运行产物不是交付物。

冻结路径不能落在可编辑路径之内，生成路径也不能与冻结路径重叠，`init` 会直接拒绝这类自相矛盾的约定。

## 3. 一次完整呈交，一次人工审阅

先把所有信息收集齐，再一次性呈交草案，内容包括：场景、要改什么不改什么、命令原文、基线结果、目标与预算（如有）、你看到的风险。人只需要做一件事：**修改**或**批准**。不要把澄清拆成十几轮零碎提问。

人修改后，按修改结果更新草案再呈交一次；人批准后才运行 `init`。

## 4. 契约规则

- **在工作克隆里 `init`**：`--repo` 指向普通的克隆根目录，不能是 `git worktree add` 出来的链接工作区。循环工作区稍后在 `start` 时绑定。
- **运行目录**：`--home` 必须是 `<repo>/.evloop/runs/<task>` 形式的**绝对路径**，并且位于之后的循环工作区之外（回滚会在工作区里执行 `git clean`，放在里面会被删掉）。
- **只在本地生效**：`init` 会把 `/.evloop/` 追加到该克隆的 `.git/info/exclude`，状态目录不会进入共享历史，也不需要改 `.gitignore`。
- **基线在克隆里跑**：`init` 在工作克隆的当前 HEAD 上运行约定命令并记录结果。命令若在克隆里留下了新的未跟踪或改动文件，会记入 `baseline.side_effects` 并告警——要么清理、要么加入忽略，循环里同样会写的位置用 `--generated` 声明。
- **交付目标分支**：`--branch-from` 默认是克隆当前分支，交付时合并回它。
- **封存**：契约保存时计算 `agreement_sha`；之后任何手工编辑都会让加载失败。约定确实需要改变时，重新澄清，然后 `init --renew`：只有新契约成功写入时，旧契约和记录才会被归档为带时间戳的 `.bak`，中途失败不会丢失原约定。
- **迁移**：运行目录随仓库搬到另一个克隆后，用 `relocate --repo <新克隆> [--worktree <新工作区>]` 重新指向。新克隆里必须已有最优提交，宪法必须保持原样。
- **格式版本**：契约带 `schema_version`，比当前工具更新的契约会被拒绝加载，提示升级。

示例骨架（各场景的完整示例见细则）：

```bash
python3 <skill>/scripts/evloop.py --home "$PWD/.evloop/runs/fix-rounding" init \
  --scenario bugfix --editable src/billing --frozen tests/billing \
  --test-cmd "python3 -m pytest -q tests/billing"
```

## 5. 进入循环前的检查清单

- [ ] 场景与完成定义已被人明确批准。
- [ ] 可编辑范围足够窄，冻结路径覆盖了全部判定依据。
- [ ] 约定命令在干净环境下可重复运行，耗时可接受。
- [ ] 基线结果符合预期（修复：失败；优化：干净跑通且噪声低于 δ；开发：蓝图校验通过、无依赖环）。
- [ ] `side_effects` 已处理或已用 `--generated` 声明。
- [ ] 优化场景：目标、方向、δ、预算、预留时间都写进了契约。
- [ ] 需要限制成本时：`--max-attempts` / `--token-budget` 已约定（任何场景可用，宪法可给默认值）。
- [ ] 完整测试较慢时：约定一个几秒内能跑完的 `--fast-cmd` 作为快速预检，它必须在基线上通过。
- [ ] `python3 <skill>/scripts/evloop.py doctor --home ...` 全部通过。

都满足后，按 [loop.md](loop.md) 创建工作区并 `start`。
