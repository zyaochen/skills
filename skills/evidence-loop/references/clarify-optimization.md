# 优化场景的澄清

优化场景的裁判只认一个数字。澄清阶段要把这个数字怎么产生、怎么比较、多大的变化才算数、花多少时间，全部定死。

## 1. 基准：可量化、单一

- 基准命令必须在输出里打印一个数字，用 `--score-regex` 提取：有捕获组时取第一组，有多处匹配时取**最后一处**；`nan`、`inf` 和非数字都视为没有分数。
- 只能有一个分数。多个指标都重要时，在澄清阶段约定一个**固定的加权公式**，由基准脚本自己算出综合分并打印；公式写进基准脚本并冻结。
- 基准脚本、数据集、夹具全部放进 `--frozen`。

## 2. 跑基线

先手工跑几次，观察分数的波动。`init` 会跑两次：一次基线，一次未改动的**对照重跑**。两次的差就是噪声，**噪声必须严格小于 δ**，否则 `init` 拒绝——在噪声之内的"改进"无法与运气区分。基线命令必须退出码为 0 且能提取到分数。

## 3. 约定限制

| 项 | 参数 | 说明 |
|---|---|---|
| 方向 | `--direction lower` / `higher` | 越低越好（耗时、内存）或越高越好（吞吐、命中率） |
| 单位 | `--unit` | 只用于报告显示 |
| 目标 | `--target` | 达标线；默认"等于也算达标"。人没给目标时**先问**；人明确说"尽量好、不设线"时可以不给，这时为纯改进模式：只在预算（时间 / 次数 / token）耗尽时交付，结论写"改进了多少"，不写"达成" |
| 严格达标 | `--exclusive` | 只有人明确说"低于 / 高于"时才加，表示等于不算 |
| 最小改进 | `--delta` 或 `--delta-pct` | 二选一。绝对值，或基线分数的百分比（基线为 0 时只能用绝对值） |
| 预算 | `--budget-minutes` | 墙钟时间上限，必填（可由宪法给默认值，但不能超过宪法的上限） |
| 预留 | `--reserve-minutes` | 预算末尾留给 verify 与交付的时间，必须小于预算；进入该窗口后不再接受新尝试 |
| 可编辑 / 生成 | `--editable` / `--generated` | 同通则 |
| 次要指标 | `--secondary-regex` + `--secondary-direction` | 可选，必须同时给出。基线上必须能提取到；之后每次尝试都要能提取到，否则判无效 |
| 简化规则 | `--prefer-simpler` | 可选。分数在 δ 内持平、次要指标未变差、且净删除代码时按"简化"接受（见 [loop.md](loop.md)） |
| 快速预检 | `--fast-cmd` | 可选。每次尝试先跑它，失败即判无效，省下完整基准的时间；基线上必须通过 |
| 次数 / token 上限 | `--max-attempts` / `--token-budget` | 可选，与时间预算并存，先耗尽者生效 |

## 4. 方向与 δ 的判定

一次尝试被**接受**，当且仅当它比当前最优**严格好出超过 δ**：

| 方向 | 接受条件 | 例：最优 100，δ=5 |
|---|---|---|
| `lower` | `新分数 < 最优 − δ` | 94 接受；95 拒绝 |
| `higher` | `新分数 > 最优 + δ` | 106 接受；105 拒绝 |

达标判断与 δ 无关：`lower` 时 `分数 ≤ 目标`（加 `--exclusive` 后为 `<`），`higher` 同理。用"严格超过 δ"而不是"超过或等于"，是为了让恰好落在噪声边界上的结果不被当成进步。

## 5. 次要指标：护栏，不是第二个目标

次要指标不参与"是否改进"的判断，只在两处起作用：简化规则要求它不变差；交付包展示它从基线到最终的变化，让人看到主指标的进步有没有拿别的东西去换。真正需要同时优化两个指标时，仍然按第 1 节约定加权综合分。

## 6. init 示例

```bash
python3 <skill>/scripts/evloop.py --home "$PWD/.evloop/runs/p99" init \
  --scenario optimization \
  --editable src/query \
  --frozen bench \
  --test-cmd "python3 bench/run.py" \
  --score-regex 'p99_ms=([0-9.]+)' \
  --direction lower --unit ms \
  --target 80 --delta-pct 3 \
  --budget-minutes 120 --reserve-minutes 10 \
  --secondary-regex 'rss_mb=([0-9.]+)' --secondary-direction lower --prefer-simpler
```

## 7. 呈交审阅

一次性给人看：基准命令与示例输出、提取正则、基线分数与对照分数（噪声）、方向、目标、δ 及其来源、预算与预留、可编辑与冻结范围。

优化是 do-while：即使基线已经达标，也至少尝试一轮再交付。达标时如果只试过一条路线、预算还有余量，`status` 的 `next` 会提示先用一条**不同的** `--route` 再试一次再 `verify`——交付包里有路线对比，人才能判断这个结果是不是唯一或最好的办法。预算耗尽而未达标时照常交付，由人决定接受现有成果还是开启新一轮（新一轮需要重新澄清并 `init --renew`）。
