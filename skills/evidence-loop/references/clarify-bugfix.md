# 修复场景的澄清

修复场景的核心是一条**复现测试**：它在修复前必须失败，修复后必须通过。没有它，"修好了"就只是一句话。

## 1. 先写复现测试

- 用最小输入稳定复现问题，断言**正确**的行为，而不是断言当前的错误输出。
- 放在会被冻结的测试目录里，让循环无法通过修改测试来"修复"。
- 如果问题依赖时间、随机数或外部服务，先把这些固定下来；不稳定的测试会让裁判的结论失去意义。

## 2. 对齐已有测试

修复可能让一些旧测试的期望变得不对。把受影响的测试列出来，**并排展示旧期望与新期望**，由人逐条确认哪些该改。确认后的改动在澄清阶段就提交到工作克隆里，再冻结——循环里不允许再动它们。

## 3. 跑基线

在工作克隆的当前提交上手工跑一次约定的测试命令，确认它确实失败、失败的原因就是这个缺陷，而不是环境问题或别的测试。`init` 会再跑一次：如果命令在未改动的源码上**已经通过**，`init` 会拒绝——这说明复现测试没有复现问题。

## 4. 红绿检查

`init` 只能看到测试在基线上失败一次。为了排除"恰好失败"（不稳定、依赖运行次数或环境）的假红，`verify` 会在临时 worktree 里检出基线源码、套上当前的冻结测试再跑一次：它必须仍然失败，修复的证据才成立。所以复现测试要**确定性地**失败，而不是偶尔失败。

## 5. 影响面

和人一起填一张表：

| 项 | 内容 |
|---|---|
| 可编辑 | 预计需要改动的源码目录（`--editable`） |
| 冻结 | 复现测试与相关测试目录（`--frozen`，必填） |
| 测试命令 | 原样记录（`--test-cmd`），包含复现测试与回归测试 |
| 生成路径 | 测试运行写出的缓存或产物（`--generated`） |
| 已知风险 | 可能受影响但测试未覆盖的行为，交付时要在评审说明里交代 |

## 6. init 示例

```bash
python3 <skill>/scripts/evloop.py --home "$PWD/.evloop/runs/fix-rounding" init \
  --scenario bugfix \
  --editable src/billing \
  --frozen tests/billing \
  --generated .pytest_cache \
  --test-cmd "python3 -m pytest -q tests/billing"
```

修复场景不接受 `--score-regex`、`--target` 等优化参数；可以用 `--max-attempts` 限制尝试次数，用 `--fast-cmd` 先跑一组快速测试。

## 7. 呈交审阅

一次性给人看：复现测试的代码与失败输出、旧测试的新旧期望对照、影响面表格、完整的 `init` 命令。人批准后再 `init`，然后按 [loop.md](loop.md) 进入循环。
