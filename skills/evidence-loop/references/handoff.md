# 交付：证据、批准、合并

## 1. 先审视自己的结论

`status` 给出 `decision: handoff` 只说明约定的规则满足了。在呈交之前，自己先过一遍：结论是否超出了证据？有没有测试没覆盖、但改动可能影响的行为？把这些写进 `review.md`（见 [visualization.md](visualization.md)）。

然后：

```bash
python3 <skill>/scripts/evloop.py --home "$RUN" verify   # 在最优提交上重跑
python3 <skill>/scripts/evloop.py --home "$RUN" report   # 生成 handoff.html
```

`verify` 会清掉之前的报告与批准；`report` 必须在最近一次 `verify` 之后运行，并且工作区干净、HEAD 即最优，否则这份交付包不能用于审批。验证失败时，交付包会写"验证失败"与"尚未完成"，不会给出成功的结论。

## 2. 呈交交付包

- 能内嵌预览就直接预览 `handoff.html`；否则给出它的**绝对路径**和 `report` 输出里的 `open` 命令。
- 用几句话概括：结论、关键证据、最大的风险或未验证项、需要人决定什么。
- 明确告诉人：批准之前不会合并，也不会删除工作区。

## 3. 批准的含义

人明确表示批准后才运行：

```bash
python3 <skill>/scripts/evloop.py --home "$RUN" approve --note "<评审人的原话>"
```

批准绑定三样东西：当前最优提交、最近一次验证的编号、交付包文件的 sha256。之后只要有新的尝试被保留、重新验证、重新生成报告，或交付包被改动，批准就自动失效，`status` 的 `approved` 变回空。没有 `--check-cmd`（且宪法没有 `guard_cmd`）的开发场景没有可以重跑的命令，批准只需要一份当前的交付包——这时人工审阅就是唯一的验证。

## 4. 各场景交付包的内容

**开发**：竣工图与蓝图并排，标出每个元素的状态（已实现 / 待定 / 缺失）、构建顺序、新增元素、元素覆盖（声明了 `accept` 的元素附带验收命令），以及竣工图是否与蓝图一致。

**修复**：运行表——基线与每次尝试的提交、裁决、退出码、增删行数、失败摘要、原始日志链接，最后一行是验证结果；约定测试是否全部通过，以及红绿检查（测试在基线源码上是否仍然失败）。

**优化**：过程图 `process.svg` 必须让人一眼看出：

- 基线点与每次尝试的分数点，按裁决着色（接受 / 拒绝）；没有分数的无效尝试在横轴上方标为 ✕；
- 保留的最优分数的阶梯线；
- 虚线目标线；
- 纵轴标注单位与方向（越低越好 / 越高越好），横轴为尝试序号。

同时写出 `caption.json`，供人或其他工具引用：

| 字段 | 含义 |
|---|---|
| `baseline` / `final` | 基线分数与记录的最优分数 |
| `improvement` / `improvement_pct` | 改进量与改进百分比 |
| `target` / `target_met` | 目标线与是否达成 |
| `attempts` / `routes` | 尝试次数与各路线的接受 / 拒绝 / 无效统计（含其中的简化次数） |
| `secondary` / `prefer_simpler` | 次要指标的基线与最终值、是否启用简化规则（约定了才有） |
| `tokens_used` | 上报的 token 累计用量 |
| `delta` / `noise` | 判定门槛与基线噪声 |
| `verification` | 针对当前最优的验证记录（没有则为空） |
| `delivered_commit` / `rerun` | 交付的提交与复跑命令 |

改进量按方向计算：`lower` 时为 `基线 − 最终`，`higher` 时为 `最终 − 基线`；百分比为改进量除以 `|基线|`（基线为 0 时不给百分比）。

## 5. 合并回去

批准后：

```bash
git -C "$REPO" checkout <branch_from>
git -C "$REPO" merge --no-ff evloop/<task>
git -C "$REPO" worktree remove ../<repo>-evloop-<task>
git -C "$REPO" branch -d evloop/<task>
```

用普通合并（不要压扁、不要变基），保留每次被接受的尝试作为历史。运行目录（`.evloop/runs/<task>`）留在本地作为审计记录，它不会进入共享历史。

## 6. 进度不等于交付

`report --progress` 的快照、`status` 里的 `continue`、未经 `verify` 的通过，都不是交付。只有"验证通过 → 当前交付包 → 人工批准"这条链完整时，才能合并。

## 7. 研究与文档的交付包

交付包额外列出：每个问题的覆盖情况与来源域名、每条被引用的论断与它的来源快照、细则评审的分数与校准结果。评审人重点看：结论是否超出了论断能支撑的范围、来源是否可信、有没有该回答却没回答的问题。

## 8. 形式化设计验证的交付包

交付包多一节"形式化设计验证"：模式、约定案例 verified 数、探针发现、输入摘要与检查器哈希；每个案例的结果与原始日志；反例的完整状态序列；"需求 → 性质 → 代码 → 回归测试"交接表；筛选结论与证据边界。结论只能写成"在指定的模型、参数和假设下，检查器完成了检查且未发现被检查性质的违例"。探针反例要逐条交人裁决（新需求、已知取舍还是建模问题），评审说明里写清每条反例的分类，详见 [clarify-formal.md](clarify-formal.md)。

## 9. 计划的交付

计划里每个任务各自走完"验证 → 交付包 → 批准"；`plan status` 为 `all done` 之后，用 `plan report` 生成 `plan.html` 给人看全局，并把自动模式下记录的假设逐条交人复核。

## 10. 沉淀规则

交付时顺带提议：这次任务里有没有值得长期冻结的路径、值得每次都跑的底线检查、合适的默认预算？有的话，建议人把它们加进[项目宪法](constitution.md)。
