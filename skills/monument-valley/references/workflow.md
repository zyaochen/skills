# 建谷工作规范

## 一、工作区与证据

每次任务使用独立工作区，维护来源清单、证据记录、章节草稿、分镜、图片、远端映射和操作日志。默认不把这些运行材料包含进可分发技能。

来源记录至少有稳定 source_id、类型、标题、真实 URL 或用户文件位置、公开/内部级别、读取状态、抓取日期、修订或内容指纹。状态区分已读取、部分读取、无权限、失效、重复和排除。

证据记录至少有 claim_id、支持的命题、source_ids、事实/转述/引语/解释类别、原始位置、时间范围、角色归属、限制。简短原话逐字核验；较长文字用转述。存在日期冲突就保留冲突，不用生成时间替代事件发生时间。

### 来源获取

- GitHub：分页清点用户仓库，保留 fork、archive 和语言；读取 README、描述、必要的发布记录。高相关仓库可检查代码，但不因读到 README 就宣称审计过实现。仓库量与作品量分开统计。
- 博客/网站：优先真实目录、RSS、已解析页面链接。先验内容类型；HTTP 200 也可能是软 404，所谓 sitemap 可能只是错误页。去重后按主题/时期分组。不要猜 URL 后当作已经核实。
- 飞书：使用有权限的专用工具或官方技能读取，递归范围以用户授权为限。无权限不是“没有内容”。不得在浏览器里绕过登录或索取凭据。
- 旧版总结：只用作索引和候选解释，逐条回到原始来源；不能与原始来源重复计为两条独立证据。

### 大语料

先建立完整清单，再给各研究代理互不重叠的 source_id 范围。请求输出：覆盖数、证据记录、思想候选、时间线、冲突、缺口、产物路径；摘要控制在约 800 字，完整记录落盘。不让代理继续生成同类递归代理。

汇总按 source_id 和内容指纹去重。全量请求的覆盖分母来自实际清点，而非猜测；关键内容只摘录时写“部分读取”，不声称完整看完。每次最多三次同类尝试，代理不可用后转为脚本抽取与分段处理。批处理不等于阅读理解，二者分别记录。

## 二、主题旅程而非履历清单

山谷的主题可以是一个人，也可以是团队、组织、项目、产品、一次事件或一个概念。先定 `subject_kind`，再按下表回答这个主题的核心问题；都不合适时用 `other`，并在封面写明它是什么。

| subject_kind | 先回答的问题 | 常见来源 | 作品庭院放什么 | 额外红线 |
|---|---|---|---|---|
| person 人物 | 这个人反复面对什么问题？判断如何改变？哪些作品使判断具体化？哪些矛盾未解？ | 博客、GitHub、演讲、用户提供的作品 | 作品、时期与本人角色 | 不推断私人动机或人生结局；称呼用本人自选 |
| team 团队 | 团队为解决什么而成立？分工与方法怎样演变？哪些交付是转折？ | 周报、复盘、OKR、内部文档 | 交付物与负责范围 | 成果归团队，不把集体产出记到某个人；成员姓名只用来源里公开的 |
| organization 组织 | 使命是什么？结构和策略在哪些节点改变？ | 官网、公告、年报、内部说明 | 业务线、产品与里程碑 | 不代表组织发布官方口径；内部材料按保密级别处理 |
| project 项目 | 要解决的问题是什么？关键设计决策与取舍？版本如何演进？还有哪些未解问题？ | README、设计文档、提交历史、发布记录、issue | 模块、版本与贡献者角色 | star、fork、下载量不等于采用或影响力；路线图不写成已交付 |
| product 产品 | 为谁解决什么？版本与功能怎样演进？用户反馈改变了什么？ | 发布说明、产品文档、需求、用户研究 | 版本、功能与使用场景 | 不捏造用户数、收入或满意度；未上线的写为计划 |
| event 事件 | 起因、过程、转折与结果各是什么？学到了什么？ | 时间线、群消息、复盘、监控记录 | 关键决策点与后续行动 | 时间以记录为准；不追责个人，结论只写来源支持的 |
| topic 概念 | 这个概念回答什么问题？有哪些流派或分歧？怎么落到实践？ | 论文、文章、教程、案例 | 代表性作品、案例或实现 | 不把一家之言写成共识；争议点标出各方来源 |
| other 其他 | 用户想让读者走完这条路后记住什么？ | 用户指定 | 用户指定 | 与上面最接近的一类共用红线 |

再设计文档：

1. 封面与入口：主题称呼（人物用自选称呼，其余用正式名称）、范围与一句有依据的核心命题。
2. 全谷地图：有序关卡节点、明确连线、可点击章节导航。
3. 来时石阶：只用有来源的年份、事件与作品；不确定日期写时间范围或未详。
4. 主线关卡：每关有一条问题、一个判断、一个空间动作和可追溯材料；关卡之间有转折，而不是彼此独立的画册。
5. 碑文长廊：少量准确短引语，分类且每句归因；正文已展示的长表不再重复。
6. 作品庭院：按上表放作品、交付物或案例，写明时期、角色与链接；没有影响数据就只介绍作品。
7. 未完之门：仍在探索的问题和可续写位置，不替主题宣布成功或终局。
8. 维护区：资料范围、缺口、更新说明和版本变更。

这是一套可裁剪结构，不是强迫每个主题拥有同样九关。偏工程可用桥、开关与塔；偏艺术可用镜廊与色岛；偏学术可用观测台和分岔路径；项目与产品可用逐层搭起的建筑；事件可用一条单向的路与岔口。隐喻只能解释已知内容，不能变成新事实。

## 三、写入、恢复和验收

创建文档后立刻保存真实 doc_id 和 URL。先写章节容器，再上传对应媒体。官方工具如要求 parent-node，应提供该文档真实现存块；媒体上传成功返回的 file token 才能写入图像块。路径或批处理语法先查当前官方能力，不复制过期命令；已验证的做法见 `feishu-ops.md`。

改已有插图（换主角、调比例、提清晰度）用原位替换，不删块重插；镜像到另一份文档时媒体须在目标文档重新上传。

每个写操作有 op_id、目标稳定章节 key、输入指纹、预期操作、状态及返回值摘要。成功后再标记 applied。超时或状态不明先回读目标块再决定重试，以防重复插入。操作失败不要因 shell 退出码为零就登记成功。

更新流程：最新快照 → 来源与内容指纹差异 → 变更清单 → 检查是否在用户授权范围 → 局部更新 → 回读。block ID 来自最新快照，不跨文档重用；删除需明确授权。保留既有用户手改，冲突时不覆盖，转为新建议块或待确认项。

认证失败只按运行环境提供的官方刷新流程处理，不编写备用取令牌逻辑、不记录令牌、不把响应转存入公开产物。其他故障按参数、权限、限流、签名失效等分类处理，最多三次，转向替代能力。

### 验收清单

- 结构：章节齐全，导航顺序与地图一致，图片实际嵌入而非只有链接。
- 证据：每个事实命题能回到来源；事实/转述/比喻分明；覆盖与缺口准确。
- 内容保留：图化前的年份、语言、标题、链接、限定词在可编辑文字中仍存在。
- 视觉：主角本相可辨、造型一致、比例符合规则；地图能走、时间线顺序正确、标签可读、画面不重用错图。
- 度量与评审：每张图的色板与比例度量通过，独立评审（不是出图方）五项分数达到下限；该批评审把对照样本判为不合格、把基准图判为全部达标，`seen` 抽查属实。
- 交付：每张图符合交付尺寸与体积；用户端能加载出图，不只是接口返回成功。
- 镜像：如有镜像文档，正文、图片数与顺序、图注、配色逐项一致。
- 去重：碑文不在正文逐字重复；不存在“如下表”却已改成图片清单的残留句。
- 语义：五个概念就是五个，不因九个方法而命名为“五镜九面”；正负提示颜色仍可区分。
- 维护：版本日志、真实修订、操作记录、待补缺口可用；恢复不重复造文档。

离线检查无法替代在线回读与视觉验收。若只能确认图片数量，明确“结构已核对，完整渲染未验证”，不要说所有视觉要求已通过。

## 四、全文校对

交付前或用户要求「再检查下全文」时，逐项过一遍；每处修改回到来源核实，汇总进更新日志，拿不准的列给用户裁决而不是自行改写。

- 称呼：主题称呼（人物的笔名、昵称，项目或产品的正式名与简称）全文统一，与来源写法一致（如「魔法师」不要混成「魔术师」）。
- 时间：同一事件的年份在时间线、关卡正文、年表中一致；状态类描述（在职、连载、暂停）以最新来源为准并前后呼应。
- 交叉引用：「见第 N 关」「恰好到站」一类指向与实际章节对得上；导航顺序与地图一致。
- 引语：逐字对照原文，补回被截短的句子；去掉行首多余空格和残留标点。
- 标题与图注：同一对象的章节标题、目录项、图注用同一名称。
- 结构残留：没有「如下表」却已改成图的句子，没有重复段落，分隔线与章节层级一致。
- 更新日志：每一行描述与文档当前实际一致（关数、主角、图片规格）；历史行不改写事实，只在新行说明变化。
